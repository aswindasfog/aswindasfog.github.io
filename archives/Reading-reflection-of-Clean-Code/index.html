《Clean Code》讀書心得

發表於2026-06-27|更新於2026-06-27|心得
|總字數:973|閱讀時間:2分鐘

這本書是講述作者認為的「Clean Code」應該長成什麼樣子，這樣的程式碼有什麼好處，並提供 Java 程式範例，讓讀者可以更容易學習。

我看的是中譯本，完整書名是《無暇程式碼 敏捷軟體開發技巧守則》，看完這本書後，我覺得這個翻譯不好，雖然作者提倡的 clean code 有很多好處，但是沒讓我感覺到完美無瑕的地步，而且書中其他地方寫到 clean 時，不是翻譯成「乾淨」就是翻譯成「整潔」，所以書名翻譯成「無暇」反而讓我有種太過吹捧作者的感覺，不然就是出版社想要一個聳動的書名，讓人想要買來看。

我認同的 clean code 原則

本書的第一部分是講述 clean code 的原則，這裡挑幾個我覺得不錯的原則來分享。

有意義的命名

使用可以展現意圖的名稱可以讓人更容易理解，且避免誤導，雖然這樣做名稱會變長，但可以因此減少註解。

不要重複自己

重複的程式碼不僅會增加空間，也使要修改的地方變多，產生錯誤的機會也增加，所以有重複的部分應該封裝成函式重複利用。

有意義的註解

註解是用來補充程式碼無法表達的意圖，而且註解沒辦法永遠跟著程式碼移動，所以要寫有意義的註解，作者舉出許多例子，像是：法律資訊、格式說明、使用的警告……等，也舉出許多反例，像是：沒說明清楚導致誤解、修改的註解應該放在原始碼管控系統……等。

好讀的編排

無論是垂直方向的空白行，還是水平方向的縮排與空白字元，適當的使用可以增加程式碼的可讀性。

整潔的測試

作者推薦採用測試驅動開發（TDD），而且一個測試只負責一個概念，這樣測試就能重複利用，且有需要重構時也不用擔心會把原有功能改壞。

我不認同的clean code原則

特別提兩個我不認同的原則。

函式要簡短

作者說函式要簡短，應該只要2~4行就好，但我覺得在考量要不要把某個複雜功能的大函式拆成小函式時，應該要優先考量的是能否重複利用，與能否增加可讀性，而不應該以程式碼行數當作考量。

類別要簡短

如同函式簡短一樣，作者建議類別要依照單一功能原則（SRP）將類別拆開，但我覺得要看需求功能，若適當的保留大類別，可以減少整體複雜度。

其他部分

本書的第二部分是作者以實際的程式來示範如何重構成 clean code，重點在於 clean code 通常都不是一次到位，而是隨著每次修改逐步到位；第三部分是作者整理出來所謂的 code smell 列表，可以說是作者經驗累績出來的知識庫，而且可以跟前面交互參照，讓人更容易了解怎樣的程式碼是不好的。

結論

簡單來說，作者認為好的程式碼就是要以可讀性、可測試性、可維護性、可擴充性為最高原則，讓寫出來的程式是穩定且可靠的，並可以逐步擴大成一個系統，因此這本書推薦給有想把程式碼寫好的人，畢竟在這個 AI 時代只是寫出功能的話，已經可以靠 vibe coding 了 ，但好的程式設計與系統架構還是有它的專業價值在。

《人月神話》讀書心得
《人月神話》是業界公認軟體專案管理的聖經，最初於 1975 年出版，而我看的是 20 週年紀念版的中譯本，雖然書中提到的軟體已經是五、六十年前的東西了，我都沒有看過與用過，但關於軟體專案管理的內容卻還是一點都不過時，接下來分享一些我覺得不錯的概念與我個人看法。 人月神話 本書第二章與本書書名同名，此章講述軟體專案不順利主要是缺乏良好的時程規劃，會造成這樣是來自於兩個錯誤的想法。 第一個錯誤想法，是因為程式設計師都是樂觀的傢伙，由於軟體是很好修改的東西，所以容易認為一切都能順利進行。 第二個錯誤想法是來自於預估排定時程所使用的人月，由於成本是使用人力與工時的乘積來計算，但工作進度卻不是如此，只有工作可以切分，且交接不用溝通時，人力與工時才可以互換，否則，增加人力勢必需要增加溝通與訓練的成本。 因此人月是一個神話，本章最後提到的Brooks定律：「在一個時程已經落後的軟體專案中增加人手，只會讓它更加落後。」到現在依然成立。 概念整體性 在第四章中作者主張在系統設計時，保有概念整體性是最重要的原則，其重點在於讓使用者有一致性的體驗，所以我認為，不管是一個人開發軟體，或是一群人開發系統，...
